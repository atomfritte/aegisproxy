# Identity and access

People sign in to the console with **single sign-on** (OpenID Connect: Microsoft Entra ID, Keycloak, Okta, Ping,
ADFS, Google Workspace, …) or with a local password. Accounts of SSO users are created just in time at the first
sign-in or ahead of time by **SCIM provisioning** from Entra ID or Okta. Automation (SOAR playbooks, CI pipelines,
ITSM connectors, scripts) uses **service accounts** with API keys. Both get one of the four roles below.

| Identity | Authentication | Managed by |
|---|---|---|
| SSO user | OIDC authorization code flow with PKCE; role and scope from IdP groups | IdP group membership (provisioned just in time) |
| SCIM-provisioned user | OIDC like an SSO user | the IdP over SCIM 2.0: created, updated, deactivated and deleted by Entra ID / Okta; role and scope from the pushed groups ([SCIM provisioning](#scim-provisioning)) |
| Local user | Password (PBKDF2-HMAC-SHA256, ≥ 12 characters, 3 character classes), login throttling | Super Admins (**Settings → Identity**) |
| Break-glass user | Local Super Admin that may use a password even when password login is disabled | Super Admins |
| Service account | `Authorization: Bearer aegis_sa_…` | Super Admins (people only) |
| SCIM client (the IdP's provisioning service) | `Authorization: Bearer aegis_scim_…`, accepted only by `/api/scim/v2` | Super Admins (people only) |

## Roles and scopes

| Role (`role`) | Scope | Typical holder |
|---|---|---|
| `SUPER_ADMIN` | everything, incl. users, service accounts, SSO, log export and Defender settings | platform owners (2–5 people) |
| `INFOSEC_APPROVER` | all server groups; BLOCK rules, threat protection, fleet, requests | security team, SOAR |
| `TEAM_LEAD_APPROVER` | only the groups in `allowed_groups`; ALLOW rules, requests, learning sessions | application/team leads |
| `OPERATOR_AUDITOR` | read-only | auditors, NOC, reporting jobs |

The full permission matrix is in [security.md](security.md#roles-rbac) and
[policy-management.md](policy-management.md#roles-and-permissions). Roles are re-read from the live account on
every request; a role, scope or password change revokes the account's existing sessions.

## Single sign-on

### How it works

1. The sign-in page shows **Sign in with &lt;display name&gt;** when SSO is enabled
   (`GET /api/public/meta` → `sso.enabled`). The button opens `GET /api/auth/sso/login[?next=/path]`.
2. The control-plane redirects to the IdP's authorization endpoint (authorization code flow,
   `response_mode=query`, **PKCE S256**, random `state` and `nonce`). `state`, `nonce` and the PKCE verifier
   travel in the HMAC-signed cookie `aegis_sso` (HttpOnly, SameSite=Lax, path `/api/auth/sso`, 10 minutes).
3. `GET /api/auth/sso/callback` checks `state`, redeems the code (the client authenticates as configured in
   `token_auth_method`: `client_secret_post`, `client_secret_basic`, automatic — post when the provider
   advertises it, otherwise basic — or [`private_key_jwt`](#client-authentication-with-a-private-key-private_key_jwt)
   without any shared secret) and validates the ID token:
   - signature with a key from the provider's JWKS (`RS256/384/512`, `PS256/384/512`, `ES256/384`; `none` and
     HMAC algorithms are rejected; unknown key ids trigger a rate-limited JWKS refresh),
   - `iss` equals the configured issuer (also checked against the discovery document),
   - `aud` contains the client ID; with several audiences `azp` must be the client ID,
   - `exp`, `nbf`, `iat` with 2 minutes clock skew, `nonce`, non-empty `sub`.
4. IdP groups are mapped to a role and scope (below), the user record is created or updated, and a normal
   console session cookie is issued. The user lands on `next` (local console paths only — no open redirects).

Issuer, discovery and token endpoints must use `https://`.

### Client authentication with a private key (`private_key_jwt`)

Instead of a client secret, the control-plane can prove its identity to the token endpoint with a short-lived JWT
signed by its own key pair (OpenID Connect Core section 9, RFC 7523). Nothing secret is shared with the IdP, so
there is no client secret to expire, leak from the IdP side or be phished; the private key never leaves the
control-plane.

| Aspect | Behaviour |
|---|---|
| Keys | Generated by the control-plane on demand (Super Admin): **RS256** with RSA-3072 (default; required by Entra ID) or **ES256** with P-256. The private key (PKCS#8) is stored encrypted like every other secret ([security.md](security.md#encryption-at-rest)) and never returned by the API. Each key comes with a self-signed X.509 certificate valid for two years. |
| Key ID | `kid` = RFC 7638 JWK thumbprint. |
| Assertion | Header `alg`, `kid`, `typ: JWT` and — because a certificate exists — `x5t` (base64url SHA-1 thumbprint, which Entra ID uses to find the uploaded certificate) and `x5t#S256`. Claims `iss` = `sub` = client ID, `aud` = the token endpoint from the discovery document (the audience Entra ID, Okta and Keycloak all accept), random `jti`, `iat` = `nbf` = now, `exp` = now + 5 minutes. Sent as `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, `client_assertion=<JWT>`; a stored client secret is never sent alongside. |
| Publication | `GET /api/auth/sso/jwks.json` (public, cacheable 5 minutes) lists the active key, a staged key and retired keys within their grace period, with `x5c`, `x5t`, `x5t#S256` and without private members. `GET /api/settings/sso/client-certificate[?kid=…&format=pem\|cer]` downloads a certificate for IdPs that need an upload. |
| Rotation | 1. *Stage new key* (`POST /api/settings/sso/client-keys`): it is published in the JWKS at once and its certificate can be downloaded, but it does not sign yet. 2. Register it at the IdP (Entra: upload the certificate; JWKS-URL IdPs see it automatically). 3. *Activate* (`POST /api/settings/sso/client-keys/{kid}/activate`): the new key signs; the previous key is **retired** — its private key is erased immediately, its public key stays in the JWKS for **7 days** so cached keys and in-flight sign-ins keep working, then it disappears. Staged and retired keys can be deleted at once (suspected compromise); the active key cannot be deleted while `private_key_jwt` is in use. |
| Validation | Enabling SSO with `private_key_jwt` requires an active key; Entra ID additionally requires an RS256 key. *Test connection* reports whether the IdP advertises `private_key_jwt` and whether an active key exists. |
| Audit | `SSO_CLIENT_KEY_GENERATED`, `SSO_CLIENT_KEY_ACTIVATED`, `SSO_CLIENT_KEY_DELETED`; the method is part of `AUTH_CONFIG_UPDATED`. |

Console: **Settings → Single sign-on → Client authentication: private_key_jwt** shows the key list, the JWKS URL,
certificate downloads (`.pem`, `.cer`), the SHA-1 thumbprint as Entra ID displays it, *Generate key* / *Stage new
key*, *Activate* and *Delete*.

| IdP | Configuration |
|---|---|
| **Microsoft Entra ID** | App registration → **Certificates & secrets → Certificates → Upload certificate**: the `.pem` or `.cer` file (RS256 key). Entra ID shows the thumbprint listed in the console. Remove the client secret afterwards. For rotation upload the staged key's certificate *before* activating it (Entra keeps several certificates). |
| **Keycloak** | Client → **Credentials → Client authenticator: Signed JWT** (signature algorithm "any" or the key's algorithm); **Keys → Use JWKS URL: on**, JWKS URL = `https://aegis.corp.example/api/auth/sso/jwks.json`. Keycloak re-reads the JWKS when an unknown `kid` arrives (at most every 10 seconds). |
| **Okta** | Application → **General → Client Credentials → Client authentication: Public key / Private key**; *Use a URL to fetch keys dynamically* with the JWKS URL, or *Save keys in Okta* and add the public key as JWK (copy it from the JWKS). Okta requires `aud` = its token endpoint, which is what AegisProxy sends. |
| Ping / others | client authentication `private_key_jwt` with the JWKS URL or the certificate. |

The JWKS URL must be reachable from the IdP (Keycloak and Okta fetch it); Entra ID needs no inbound access.

### Microsoft Entra ID

1. **Entra admin center → App registrations → New registration**: name `AegisProxy`, single tenant, redirect URI
   platform **Web**: `https://aegis.corp.example/api/auth/sso/callback` (`AEGIS_PUBLIC_URL` +
   `/api/auth/sso/callback`).
2. **Certificates & secrets → New client secret**. Note the expiry and rotate it before it lapses.
3. **Token configuration → Add groups claim**: *Security groups* (or *Groups assigned to the application*), ID
   token: *Group ID*. Alternatively define **app roles** and set the groups claim to `roles`.
4. **Enterprise applications → AegisProxy → Properties**: *Assignment required = Yes*, then assign the groups
   that may use the console.
5. Console: **Settings → Identity → Single sign-on**: provider *Microsoft Entra ID*, **Directory (tenant) ID as
   GUID** (a domain name is rejected: Entra issues tokens for the GUID issuer), client ID, client secret, the group object IDs (or app role
   values) → roles. **Test connection**, save, sign in from a private browser window.

Group overage: when a user is in more than ~200 groups, Entra ID omits the `groups` claim and sends a
reference instead. AegisProxy then refuses the sign-in with `sso_error=group_overage` rather than guessing.
Use *Groups assigned to the application* or app roles to keep the claim small.

The Entra object ID (`oid`) is used as the stable user identifier; the issuer is
`https://login.microsoftonline.com/<tenant>/v2.0`.

### Generic OIDC (Keycloak, Okta, Ping, ADFS, Google Workspace)

| Setting | Keycloak | Okta | Ping / ADFS / others |
|---|---|---|---|
| Client | OpenID Connect, *Client authentication* on, *Standard flow* | OIDC *Web application* | confidential client, authorization code |
| Redirect URI | `https://aegis.corp.example/api/auth/sso/callback` | same | same |
| Issuer URL | `https://kc.corp.example/realms/<realm>` | `https://<org>.okta.com` or `…/oauth2/<server>` | issuer of the discovery document |
| Groups claim | client scope mapper *Group Membership*, claim `groups`, *Full group path* off | *Groups claim filter* in the ID token | any claim with a string or string array |
| Client authentication (`token_auth_method`) | automatic | `client_secret_basic` (Okta default for web apps) or switch the app to *Client secret (POST)* | as configured at the IdP |

Console fields (`provider: oidc`): `issuer_url`, `client_id`, `client_secret`, optional `scopes` (default
`openid profile email`; add `groups` if your IdP requires it), `token_auth_method` (empty = automatic,
`client_secret_post`, `client_secret_basic`, `private_key_jwt`), `username_claim` (default
`preferred_username`), `groups_claim` (default `groups`), `display_name` (button label).

### Group to role and scope mapping

| Field | Meaning |
|---|---|
| `group_role_map` | IdP group (Entra: object ID or app role value; others: group name as sent) → role. When a user is in several mapped groups, the **most privileged role wins** (Super Admin > InfoSec > Team Lead > Auditor). |
| `group_scope_map` | IdP group → list of server group IDs. Team Leads receive the union of the groups mapped from all their IdP groups. Super Admins and InfoSec always get `*`, Auditors no scope. |

A user without any mapped group cannot sign in (`sso_error=not_authorized`). Enabling SSO requires a client ID,
the tenant ID (Entra) or issuer URL, and at least one role mapping.

### Provisioning and deprovisioning

- **Just in time**: the first successful sign-in creates the user (`auth_provider: "oidc"`, `external_id` =
  digest of issuer and subject). User names come from `username_claim`; `@` is replaced by `.` (unless the claim
  is `email`), invalid names become `sso-<id>`, and a clash with a local account gets a suffix — an IdP user can
  never take over a local account by name.
- **Every sign-in** re-applies the mapping. A role or scope change is audited (`USER_ROLE_SYNCED`) and revokes
  older sessions.
- **Deprovisioning**: when a known user signs in without a mapped group (removed from the IdP group), the
  account is disabled and its sessions are revoked immediately (`LOGIN_SSO_DENIED`). Users deleted in the IdP
  can no longer sign in; their current session ends at the latest after `AEGIS_SESSION_TTL` (default 8 h) — disable
  the account in the console to cut it immediately. The posture check *No accounts unused for 90 days* lists
  leftovers.
- Roles of SSO users are managed through the IdP mapping only; the console refuses manual role changes for them.
- With [SCIM provisioning](#scim-provisioning) accounts exist before the first sign-in and deprovisioning takes
  effect immediately instead of at the next sign-in attempt.

### Permissions and testing

Only **Super Admins** (people, not service accounts) can change the SSO configuration — whoever controls the
group mapping controls who becomes administrator. Every change is audited (`AUTH_CONFIG_UPDATED`). The client
secret is write-only (stored encrypted, see [security.md](security.md#encryption-at-rest)); an empty or masked
value keeps the stored secret.

`POST /api/settings/sso/test` (Super Admin) fetches the discovery document and validates the issuer and
endpoints for the stored or the submitted (unsaved) configuration and returns the redirect URI to register, the
provider's `token_endpoint_auth_methods` and, for `private_key_jwt`, the JWKS URL and `warnings` (method not
advertised, no active client key).

Sign-in errors are shown on the login page (`/login?sso_error=<code>`) and logged with details:

| Code | Meaning |
|---|---|
| `configuration` | SSO configuration incomplete or invalid |
| `provider_unreachable` | discovery document not reachable |
| `idp_<error>` | the IdP returned an error (e.g. `idp_access_denied`) |
| `session`, `state` | login cookie missing/expired or `state` mismatch — start again |
| `token`, `id_token` | code exchange or ID-token validation failed (see control-plane log; with `private_key_jwt` e.g. `invalid_client` when the IdP does not know the key — certificate not uploaded, JWKS URL wrong or unreachable) |
| `group_overage` | the IdP omitted the groups claim |
| `not_authorized` | none of the user's groups is mapped to a role (for SCIM-managed accounts: none of their SCIM groups) |
| `account_disabled` | the account was locked by an administrator, or deactivated/deleted by SCIM provisioning |
| `disabled`, `provisioning` | SSO switched off meanwhile / user record could not be written |

## SCIM provisioning

Microsoft Entra ID and Okta can manage console accounts over **SCIM 2.0** (RFC 7643/7644): they create accounts
before the first sign-in, keep names and e-mail addresses current, push group memberships and — most
importantly — deactivate or delete accounts the moment a person leaves or loses the assignment. AegisProxy then
disables the account and revokes its sessions immediately.

### How it works

| Topic | Behaviour |
|---|---|
| Endpoint | SCIM base URL `<AEGIS_PUBLIC_URL>/api/scim/v2` (below `/api/` like every other route, so reverse proxies and ingress rules need nothing extra). Resources `/Users` and `/Groups`, discovery `/ServiceProviderConfig`, `/ResourceTypes`, `/Schemas`, searches `/Users/.search`, `/Groups/.search`, `/.search`. Media type `application/scim+json`; errors are SCIM error documents. |
| Authentication | Bearer token `aegis_scim_…` created by a Super Admin (shown once, SHA-256 stored, expires after at most 730 days, up to 5 tokens for rotation without downtime). The SCIM endpoints accept nothing else — no session cookies, user tokens or service-account keys — and SCIM tokens are not valid for any other API route. While SCIM is disabled every request gets `403`. |
| Supported operations | `POST`, `GET` (by id, list with `filter`, `startIndex`, `count` ≤ 200, `attributes`, `excludedAttributes`), `PUT`, `PATCH` (`add`/`replace`/`remove`, path-less values, value filters such as `emails[type eq "work"].value` and `members[value eq "…"]`), `DELETE`; ETags (`meta.version`, `If-Match`, `If-None-Match`). No bulk, sorting or password changes. |
| Filters | All RFC 7644 operators (`eq ne co sw ew gt ge lt le pr`, `and`, `or`, `not`, grouping, value paths). `userName`, `displayName`, e-mail addresses compare case-insensitively, `id` and `externalId` case-exactly. |
| User attributes | Stored: `userName` (unique), `externalId`, `active`, `displayName`, `name` (`givenName`, `familyName`, `formatted`), `title`, `emails`, enterprise extension `department`. Everything else an IdP sends (phone numbers, addresses, manager, roles, **passwords** …) is accepted and discarded, so default attribute mappings work unchanged. |
| Console account | `auth_provider: oidc`, no password. Username from `userName` like single sign-on derives it (`a.b@corp.example` → `a.b.corp.example`); if the name is taken by another account a suffix is added — SCIM never takes over a local or break-glass account, and local accounts are never SCIM resources (`404`). |
| Roles and scopes | **SCIM is authoritative for the accounts it manages.** Their role and Team Lead scope come from the SCIM groups they are members of, matched with the single sign-on `group_role_map` / `group_scope_map`; each group matches by its `displayName` **and** its `externalId` (Entra ID sends the group object ID there, so existing object-ID mappings keep working). The most privileged mapped role wins; Super Admin is only granted when a group is explicitly mapped to it. The groups claim of the ID token is not used for these accounts. An account in no mapped group stays **disabled** (role empty, shown as *No mapped SCIM group*). Membership changes, group renames, group deletion and changes of the mapping apply immediately and revoke the account's sessions when the role or scope changes (`USER_ROLE_SYNCED`). |
| Deprovisioning | `active: false` (PATCH or PUT) or removal from the last mapped group disables the account and revokes all sessions at once (`USER_DEPROVISIONED_SCIM`); `active: true` re-enables it (`USER_REACTIVATED_SCIM`). `DELETE` disables it, revokes sessions, removes it from all SCIM groups and stops serving it (`404`); the record stays for the audit trail and is revived if the same user is provisioned again. A deactivated or deleted account cannot sign in with SSO (`sso_error=account_disabled`). An administrator lock in the console survives SCIM updates, and an administrator cannot enable an account the IdP deactivated. |
| Linking to single sign-on | The first sign-in lands on the provisioned account when the SCIM `externalId` equals the token subject (Entra ID: map `externalId` ← `objectId`, which is the `oid` claim; Okta: the Okta user id is both `externalId` and `sub`) or, otherwise, when the SCIM `userName` equals the username claim (`preferred_username`, the UPN). E-mail addresses are never used for linking because users can change them in some IdPs. Ambiguous matches link nothing. Audited as `USER_LINKED_SSO`. |
| Existing SSO users | Accounts created just in time before SCIM was enabled are taken over when SCIM provisions the same person (same subject via `externalId`, or same username) instead of being duplicated (`USER_LINKED_SCIM`). |
| Groups | `displayName` is required and unique (case-insensitive). Members must be SCIM-provisioned users; references to local accounts, unknown ids and nested groups are ignored (noted in the audit summary). |
| Audit | `USER_PROVISIONED_SCIM`, `USER_LINKED_SCIM`, `USER_UPDATED_SCIM`, `USER_DEPROVISIONED_SCIM`, `USER_REACTIVATED_SCIM`, `USER_ROLE_SYNCED`, `GROUP_PROVISIONED_SCIM`, `GROUP_UPDATED_SCIM`, `GROUP_DELETED_SCIM`, `SCIM_CONFIG_UPDATED`, `SCIM_TOKEN_CREATED/ROTATED/REVOKED`; the actor is `scim:<token name>`. |
| Limits | 20,000 SCIM users, 5,000 groups, 50,000 members per group, 8 MiB per request, 1,000 PATCH operations per request. |

Console: **Settings → Single sign-on → Provisioning (SCIM)** (Super Admins; InfoSec read-only): enable/disable, the
base URL with copy button, number of provisioned and enabled accounts and groups, time of the last change and of
the last request, tokens (generate — shown once —, rotate, revoke). Provisioned accounts carry a **SCIM** badge
in **Identity & access**.

### Microsoft Entra ID

1. Configure single sign-on first (same enterprise application / app registration) and map the groups to roles,
   preferably by **group object ID** (works for both the token's `groups` claim and SCIM).
2. Console: **Settings → Single sign-on → Provisioning (SCIM)** → enable, **Generate token**, copy it.
3. Entra admin center → **Enterprise applications → AegisProxy → Provisioning → Get started**, provisioning
   mode **Automatic**:
   - **Tenant URL**: `https://aegis.corp.example/api/scim/v2`
   - **Secret Token**: the token → **Test Connection** (Entra queries a random `userName`; AegisProxy answers with
     an empty list) → Save.
4. **Mappings → Provision Microsoft Entra ID Users**: keep `userName` ← `userPrincipalName`, `active` ←
   `Switch([IsSoftDeleted], …)`, `displayName`, `emails[type eq "work"].value` ← `mail`, `name.givenName`,
   `name.familyName`, `title` ← `jobTitle`, `urn:…:enterprise:2.0:User:department` ← `department`. **Change
   `externalId` from `mailNickname` to `objectId`** so that the first single sign-on (which identifies Entra users
   by `oid`) lands on the provisioned account; without it, linking falls back to `userName` = UPN =
   `preferred_username`, which also works. Unsupported target attributes can stay — they are ignored.
5. **Mappings → Provision Microsoft Entra ID Groups**: keep `displayName`, `externalId` ← `objectId`, `members`.
6. **Users and groups**: assign the groups that are mapped to roles; **Settings → Scope: Sync only assigned users
   and groups**; **Provisioning Status: On**. Entra ID provisions every 40 minutes; *Provision on demand* tests a
   single user immediately.
7. Unassigning a user or blocking sign-in makes Entra send `active: false` (account disabled at once); deleting
   the user sends `DELETE` after the soft-delete period.

### Okta

1. Use the OIDC app integration of the console (or a separate SAML/SWA app) and enable **Provisioning → SCIM**
   (*General → App Settings → Provisioning: SCIM*).
2. **Provisioning → Integration**:
   - **SCIM connector base URL**: `https://aegis.corp.example/api/scim/v2`
   - **Unique identifier field for users**: `userName`
   - **Supported provisioning actions**: Import New Users and Profile Updates, Push New Users, Push Profile
     Updates, Push Groups
   - **Authentication Mode**: **HTTP Header** → *Authorization: Bearer*: paste the token (Okta sends it as
     `Authorization: Bearer <token>`) → **Test Connector Configuration**.
3. **Provisioning → To App**: enable **Create Users**, **Update User Attributes**, **Deactivate Users**.
4. **Assignments**: assign people or groups. **Push Groups**: push every group that is mapped to a role (Okta
   sends the group name as `displayName`; map that name in `group_role_map`).
5. The Okta user id is both the SCIM `externalId` and the OIDC `sub`, so the first sign-in links automatically.
   Deactivating or unassigning a user in Okta sends `active: false`.

### Security considerations

- The SCIM token can create accounts and, through group membership, grant every mapped role including Super Admin
  if a group is mapped to it. Treat it like an IdP admin credential: keep it only in the IdP, give it an expiry,
  rotate it (new token → update IdP → revoke old), and watch `SCIM_TOKEN_*` and `USER_ROLE_SYNCED` audit events.
- Map Super Admin only to a small, protected IdP group (Entra: role-assignable group / PIM; Okta: admin-managed group).
- SCIM never creates passwords; provisioned people still authenticate at the IdP with its MFA and conditional
  access. Local and break-glass accounts cannot be read, changed or deleted over SCIM.
- Failed SCIM authentications are logged with the source address, counted in `aegis_scim_auth_failures_total` and
  throttled per source address like password sign-ins (20 failures lock the address, exponential up to 15 minutes);
  restrict `/api/scim/` at the reverse proxy to the IdP's provisioning egress ranges where possible (Okta publishes
  its IP ranges; Entra provisioning uses the `AzureActiveDirectory` service tag).
- Deleting a SCIM-managed account in the console is possible but the IdP re-creates it on its next cycle; offboard in
  the IdP instead.

## Break-glass accounts

Break-glass accounts guarantee access when the IdP is unavailable or misconfigured.

- Only Super Admins can be break-glass accounts (`break_glass: true` on the user).
- With **local login disabled** (`allow_local_login: false`), only break-glass accounts with a password may
  use the password form. Every such sign-in writes the audit event `BREAK_GLASS_LOGIN` and raises a high-severity
  `BREAK_GLASS_LOGIN` security event (Teams/Slack and every log export destination with the audit or security
  stream; the Sentinel package contains an analytics rule for it).
- Password login can only be disabled when SSO is enabled and at least one active break-glass Super Admin with a
  password exists; the last such account cannot lose its flag while local login is disabled.
- The bootstrap `admin` is a break-glass account. On the upgrade to 2.1 all local Super Admins are marked as
  break-glass (unless one already was) so nobody loses access — remove the flag from personal accounts afterwards.

Recommended practice:

1. Keep **one or two** break-glass accounts (the posture check warns outside 1–2), named so that they are
   recognizable (`breakglass-1`).
2. Long random passwords (≥ 24 characters), stored offline in a safe or a vault with dual control; nobody uses
   them day to day.
3. Disable password login for everybody else once SSO works (`allow_local_login: false` in the SSO settings).
4. Test the procedure every quarter (sign in, verify the alert reached the SOC, sign out, rotate the password).
5. Rotate the password after every use and review the audit trail of the session.

## Service accounts

Non-human identities for automation, managed in the console or through `/api/service-accounts` (Super Admins
only; service accounts cannot manage service accounts).

| Property | Rule |
|---|---|
| Key | `aegis_sa_` + 43 random characters, shown **once** on create and rotate; only its SHA-256 is stored, `key_prefix` identifies it |
| Role | `INFOSEC_APPROVER`, `TEAM_LEAD_APPROVER` (requires concrete `allowed_groups`) or `OPERATOR_AUDITOR` — never Super Admin |
| Expiry | mandatory, 1 hour to **730 days** (default 365); expired keys are rejected |
| Source networks | `allowed_cidrs` (single IPs allowed); empty = any address. The client address honours `AEGIS_TRUSTED_PROXIES` |
| Lifecycle | rotate (old key invalid immediately), disable/enable, delete; `last_used_at` / `last_used_ip` (recorded at most every 10 minutes) |
| Restrictions | cannot approve change requests (four-eyes needs people), cannot change SSO, Defender, log export, users or service accounts |

Requests of a service account appear in the audit trail as `sa:<name>`. The posture page warns about keys that
expire within 14 days and about accounts without a CIDR restriction. `GET /api/auth/me` returns
`{service_account: {id, name, role, allowed_groups}}` for a key — useful as a connectivity check.

```bash
# create (Super Admin session or token)
curl -s -H "$J" -H "Authorization: Bearer $ADMIN_TOKEN" https://aegis.corp.example/api/service-accounts -d '{
  "name":"soar-sentinel","description":"Sentinel playbook: quarantine hosts","role":"INFOSEC_APPROVER",
  "allowed_cidrs":["10.40.8.0/24"],"expires_at":"2027-06-30T00:00:00Z"}'
# → {"service_account":{…,"key_prefix":"aegis_sa_Xy3"},"api_key":"aegis_sa_…"}   (store it in your vault)
KEY=aegis_sa_…

# SOAR: quarantine a host by name (or "ip"); "quarantined": false releases it (InfoSec role)
curl -s -H "$J" -H "Authorization: Bearer $KEY" https://aegis.corp.example/api/servers/quarantine \
  -d '{"hostname":"web-17.corp.example","reason":"Sentinel incident 4711: C2 beaconing"}'

# ITSM: open access requests (Auditor role is enough for reading)
curl -s -H "Authorization: Bearer $KEY" 'https://aegis.corp.example/api/requests?status=pending&overdue=true'

# Policy as code in CI: export, review, import as drafts (dry run first)
curl -s -H "Authorization: Bearer $KEY" https://aegis.corp.example/api/policy-sets/export > policy.json
jq '{dry_run:true, bundle:.}' policy.json | curl -s -H "$J" -H "Authorization: Bearer $KEY" \
  https://aegis.corp.example/api/policy-sets/import -d @-

# rotate the key (returns the new key once)
curl -s -X POST -H "Authorization: Bearer $ADMIN_TOKEN" https://aegis.corp.example/api/service-accounts/<id>/rotate
```

`J='Content-Type: application/json'`. Hostname matching for `/api/servers/quarantine` accepts the FQDN or a
unique short name; ambiguous short names are refused.

## Session security

| Aspect | Behaviour |
|---|---|
| Cookie | `aegis_session`: HttpOnly, Secure on `https://`, SameSite=Strict (`AEGIS_COOKIE_SAMESITE`) |
| Lifetime | `AEGIS_SESSION_TTL` (default `8h`, 5 min – 168 h) |
| CSRF | state-changing cookie requests need `X-Requested-With` and a same-origin (or `AEGIS_CORS_ORIGINS`) `Origin` |
| Revocation | logout, password change/reset, role/scope change, account disable, SSO deprovisioning |
| Throttling | 5 failed logins lock the account key, 20 the source IP (exponential, up to 15 minutes) |
| API tokens | `POST /api/auth/login` without `X-Requested-With` returns a bearer token with the same lifetime — prefer service accounts for automation |
